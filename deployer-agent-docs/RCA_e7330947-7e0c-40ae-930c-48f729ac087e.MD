# RCA — Live vs Preview mismatch (contact settings) — domainly-gulf / menasti.com

## Summary
The live/preview contact mismatch is a **production-database DATA staleness problem, NOT a stale frontend build and NOT missing migration code in the deployed image.** The deployed backend and preview backend behave identically for this endpoint; only the underlying `settings` document differs between the two databases.

## Evidence

### 1. Deployed build is the latest, and is a DB-passthrough
- Active run `e7330947-7e0c-40ae-930c-48f729ac087e` (type=redeploy, trigger=secret_change, completed 2026-09-28T07:49Z) is the newest run — no newer deploy exists. So production is serving the latest deployed snapshot; nothing is "behind" in terms of deploys.
- The deployed source snapshot's `/api/public/settings` handler (`backend/routers/public.py`) is a **raw DB passthrough**:
  ```python
  @router.get("/settings")
  async def public_settings():
      s = await db.settings.find_one({"_key": "platform"}, {"_id": 0})
      return s or {}
  ```
- `grep contact_details_version` across the entire deployed `backend/` returns **nothing** — `contact_details_version` is NOT a code concept. It is a field that lives on the settings document in the database. The endpoint returns whatever fields the document happens to carry. So its presence in preview and absence in prod is purely a data difference, not a code-version difference.

### 2. Production DB settings document is the OLD data
`mongo_query` on the deployed DB (`domainly-gulf-test_database`, `settings` collection, `_key=platform`) returns:
- `contact_email`: **info@manasati.sa**
- `contact_phone`: **+966500000000**
- `contact_details_version`: **absent**
- `brand_identity_version`: 1, logo `/brand/logo.webp`, navy/blue palette — matches preview.

Preview (reported by main agent) has the updated data: `contact_email=jaberra72@gmail.com`, `contact_phone=0544354420`, `contact_details_version=1`, same brand/logo/palette.

## Root cause
The `settings` document was edited in the **preview** database (via the admin update-settings flow / seed) **after** the initial deployment's one-time DB migration. Redeploys — including the secret_change redeploy that produced the current live run — **do NOT re-copy the preview database into the production database.** Only the initial deploy (or an explicit mongo migration) moves DB data. Therefore production still holds the original contact values captured at first deploy, while preview has the newer edits. Because the endpoint just echoes the DB document, the live site shows the stale contact info.

The shared fields (brand_identity_version, logo, palette) match because they were already correct at initial-deploy time and were not changed afterward — which is why only the contact fields diverge.

## Required step (DATA only — no deploy, no code change)
Update the **production** `settings` document to match preview. Options, all via the UI (no redeploy needed since the endpoint reads live DB):
1. Deployment Panel → **Database (DB Manager)**: copy the preview `settings` document (`_key=platform`) into production, or edit the production document's `contact_email`, `contact_phone`, and add `contact_details_version` directly; **or**
2. Log into the live admin at menasti.com and re-save the contact settings (the admin `update_settings` endpoint writes to the production DB).

This is production data mutation, which was explicitly **not authorized** in this diagnostic request — reported as the required action only.

## Explicitly ruled out
- **Stale frontend build**: no — brand/logo/palette match, and the contact values are served from the DB by the backend, not baked into the frontend bundle.
- **Missing migration code in deployed image**: no — `contact_details_version` is a data field, not code; the deployed endpoint is a raw passthrough.
- No owner account, secrets, site data, or domain bindings were touched. Domains menasti.com / www.menasti.com remain verified and live.
