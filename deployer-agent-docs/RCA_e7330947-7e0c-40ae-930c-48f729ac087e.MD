## Root cause
The domain the user is asking about — **`mansati.com`** — is **NOT bound to this deployment.** The domain that was added/verified is **`menasti.com`** (different spelling). These are two distinct hostnames.

`mansati.com` (and its `www`) currently resolve in public DNS to `45.79.167.180, 45.33.83.100, 66.175.209.179, 96.126.111.165` (Linode ranges) with nameservers `meilun.ns.giantpanda.com` / `chichi.ns.giantpanda.com` — i.e. a registrar/parking host, NOT Emergent's Cloudflare edge. That is exactly why:
- HTTPS to `mansati.com`/`www` fails TLS validation (no cert exists for `mansati.com` — the platform only issued certs for `menasti.com`/`www.menasti.com`).
- The crawler sees a generic "Checking your browser" interstitial (the parking/anti-bot page at those IPs), not the app.

The platform side is healthy: the app is live on `.emergent.host` and correctly bound + SSL-active on `menasti.com`/`www.menasti.com`. The failure is entirely that `mansati.com` was never attached and its DNS points elsewhere.

## What the user must decide / do
This needs a user decision because only they know which spelling is the intended brand domain (`mansati.com` vs `menasti.com`):

1. **If `menasti.com` is the intended domain:** it is already live and working — visit https://menasti.com. Nothing more to do; the earlier "deployment started" notification completed successfully.
2. **If `mansati.com` is the intended domain:** it must be added as a new custom domain in Deployment Panel → Domains. The panel will then display the exact DNS record to create (Cloudflare custom-hostname CNAME/validation target) — that per-app record is generated at add-time and cannot be pre-fetched here. The user must set that record at the `mansati.com` registrar (currently on giantpanda NS pointing to Linode IPs), then wait for verification + SSL issuance. The existing `menasti.com` records are NOT a valid target to copy for `mansati.com`.
